# Потоковая система Predictor Dispatch

Система использует сохранённый **CatBoost optuna-features-v2 на 69 признаках**.
Веса не переобучались; политика очистки и исходные CSV не изменены. История
обучения и альтернативные модели не входят в публичную поставку.

## Запуск

Нужен работающий Docker Engine с Compose. Из корня репозитория:

```bash
SPEED=10 docker compose up --build -d
docker compose ps
```

Общий образ `predictor-runtime:local` собирается только сервисом `ml`;
`backend` и `emulator` используют тот же образ. Это исключает конфликт
одновременной записи одного тега при первой параллельной сборке Docker.

- Дашборд: <http://localhost:8080>.
- Swagger backend: <http://localhost:8000/docs> (также `/docs` на порту 8080).
- Метрики: <http://localhost:8000/api/metrics>.
- Управление replay: <http://localhost:18080/docs>.
- ML доступен внутри Compose как `http://ml:8001`.

`SPEED` — отношение виртуальных секунд к реальным, диапазон 0.1–120. По умолчанию
выбирается самое плотное получасовое окно **по временам запросов**, без просмотра
исходов; replay начинается за 5 минут до него для прогрева окон. `REPLAY_SPLIT=test`
по умолчанию; допустим также `train`. Новая модель обучена только на разрешённых
train-заданиях. `source=live` означает обработку текущего replay-потока,
а не подключение к сегодняшнему транспорту города.
Можно явно задать начало в шкале датасета:

```bash
START_TIME='2026-01-06 10:00:00' SPEED=30 docker compose up -d
```

Порты хоста переопределяются через `DASHBOARD_PORT`, `BACKEND_PORT`, `EMULATOR_PORT`.
Порты публикуются только на localhost. Веса и данные смонтированы read-only,
CSV не копируются в образы. Compose не отправляет их на внешние сервисы.

Остановка: `docker compose down`. Для нового replay перезапустить **backend и
emulator вместе**: `docker compose restart backend emulator`. Состояние, журнал
прогнозов и онлайн-метрики находятся в памяти; перезапуск начинает новую сессию.
В конце данных время останавливается, статус становится `finished`, автоматического
зацикливания и переписывания старых алертов нет.

Локальный запуск без Docker (Python 3.12):

```bash
python3.12 -m venv .venv-services
.venv-services/bin/python -m pip install -r tests/requirements.txt
SPEED=10 .venv-services/bin/python scripts/run_dispatch_local.py
```

Запускаются четыре процесса на тех же localhost-портах; Ctrl-C завершает их.
Локальный frontend gateway из `dashboard/server.py` заменяет nginx для разработки.

## Модули

| Контейнер | Реализация | Назначение |
|---|---|---|
| emulator | `backend/emulator/app.py` | CSV → NDTP TCP, часы replay, запросы и опубликованные исходы |
| backend | `backend/app.py` | TCP/CRC/Nav00, причинная очистка, признаки, состояние, REST, WebSocket |
| ml serving | `ml/service/` | Загрузка CatBoost optuna-features-v2 один раз, батчевый инференс |
| dashboard | `dashboard/` | Разметка Claude Design v3, адаптер живых данных, nginx |

Redis не нужен для однопроцессного демо. Backend запускать с **одним worker**:
владелец TCP, часов и состояния должен быть один.

Оригинал фронтенда: выгрузка `PredictorApp v3.dc.html` из папки пользователя
`Downloads/Дашборд Predictor Dispatch`. Сохранена структура интерфейса и стили.
`dashboard/layout.html` — адаптированный шаблон; `live.js` — логика данных;
`scripts/build_dashboard.py` собирает `index.html`. React/ReactDOM/Babel находятся
в `dashboard/vendor`, `support.js` изменён только для локальных URL библиотек.
Зависимости CDN, внешние шрифты и mock-карта исключены из рабочего интерфейса.

## Протокол и время

`backend/ndtp.py` реализует NPL/NPH, CRC-16/Modbus со свапом, handshake и Nav00
из спецификации раздачи. `readexactly` обрабатывает фрагментацию TCP; неверный CRC,
неполные пакеты и неподдерживаемые сервисы не попадают в очистку.

**Replay расширяет протокол явно:** private NPH service `65500`, type `1` содержит
JSON для `hello`, `packet_metadata`, `query`, `fact`, `clock`. Это не стандартные
датчики NDTP. Перед каждым стандартным Nav00 приходит `packet_metadata` с исходной
CSV-строкой и `seq`; peer/request сверяются. Метаданные нужны для сохранения
дробных измерений, пропусков, больших строковых packet_id и обоих времён CSV:
стандартный Nav00 этих полей не сохраняет. Штатный бинарный образ из раздачи
остаётся нетронутым; новый replay — отдельная реализация.

Число в timestamp для replay — **кодирование naive wall time датасета**, а не
назначение ему UTC/Москвы. В API время — ISO-строка **без часового пояса**.
Для настоящего терминала с Unix time нужен явный адаптер часового пояса и реестр
unit→vehicle. Нет утверждения о готовой интеграции с произвольным промышленным NDTP.

События упорядочены по времени получения и seq; пакеты с тем же временем идут
перед запросом, затем факт. На запросе выполняются ingest → advance(T) → snapshot.
Backend использует существующие `ml.features.describe`, `History`, `ContextFeatures`.
ML получает 69 причинных признаков, включая девять детерминированных
производных от дистанции, горизонта, скорости и охвата окон. Пропуски передаются как JSON null
и восстанавливаются в NaN. `cur_dev_s` обязателен.

## Что именно прогнозируется

Вход запроса — ТС, T, целевое событие плана, плановое время и доступная на T
подсказка `cur_dev_s`. Они воспроизводятся из разрешённых train/test входных колонок.
Модель выдаёт **факт−план в секундах на заданной остановке**, не траекторию на каждой
секунде и не вероятность. `forecast_deviation_15_min` — это прогноз на заданном
событии с горизонтом 10–15 минут; точное время — `forecast_event_time`.

`POST /predict`, `GET /health`, `GET /model/info` реализованы; `/model/info` содержит
список признаков и ограничения локальной MAE. `POST /train` возвращает 501 с
объяснением: обучение намеренно выключено. Перед загрузкой сверяется SHA-256
файла весов по сохранённому контракту модели.

Новый алерт создаётся при прогнозе >120 секунд, только если в момент **завершения
инференса** до планового события осталось от 10 до 15 минут. `issued_at` никогда
не подставляется из старого T. Задержавшиеся ответы вне окна отбрасываются.
Risk: `risk` при >2 мин, `high` при >5 мин; это пороги величины опоздания, не
калиброванные вероятности. Выданный прогноз в журнале не переписывается.

## Честные ограничения интерфейса

- Лента справа показывает ETA **следующей сопоставленной остановки**: плановое время,
  ожидаемое прибытие и оценку опоздания. Если целевое событие ML совпадает со
  следующей остановкой, используется его прогноз. В остальных случаях ETA считается
  как плановое время плюс последнее доступное `cur_dev_s` и явно помечается методом
  `current_deviation_next_stop_eta`; этот baseline не выдаётся за результат ML.
- Прогнозы optuna-features-v2 относятся к явно заданным событиям с
  горизонтом 10–15 минут. Они остаются на графике и в журнале для оценки, но не
  переименовываются в прогноз следующей остановки.
- `plan-<tr_id>` — **план одного ТС**, не реальный номер маршрута. В данных нет
  реестра маршрутов, направлений, типа транспорта или дорожных полилиний.
- GPS проецируется на временно подходящие прямые между плановыми точками, с
  отказом при расстоянии >500 м. Это приближение по хордам, не road map matching.
- Средняя скорость сегмента — среднее принятых скоростей за последние 300 секунд
  после наблюдаемого входа на текущую хорду; простой — существующий causal detector.
- Двери, интервалы между соседними ТС, пачки/разрывы, вероятность и индивидуальный
  диапазон ± неизвестны и остаются null/пустыми. Не выдавать MAE за интервал прогноза.
- Причина алерта — превышение прогнозом порога. ДТП, ремонт, перегрузка и причины
  простоя без внешнего источника не утверждаются.
- График показывает план, **опубликованные разрешённые факты** и точечные прогнозы.
  Не рисует выдуманную непрерывную фактическую или прогнозную траекторию.
- What-if — прозрачная арифметика поверх последнего прогноза. Удержание добавляет
  время; сокращение будущей стоянки условно экономит ограниченное время; резерв
  не меняет опоздание существующей машины. Для расчёта интервалов данных нет.
  Сценарии не отправляют команды транспорту и не меняют исходный прогноз модели.

## Оценка по мере наступления событий

Эмулятор отдельно читает **только разрешённые** исходы train/test, отбрасывая
синтетические и скрытые event ID до преобразования target. Backend не монтирует
`labels/`. `fact` публикуется не раньше max(плановое время, фактическое прибытие).
До этого evaluator не имеет значения факта. Отсутствие факта не считается
отсутствием опоздания: через час непроверенный алерт становится `unverified`.

`/api/metrics` отдаёт MAE в минутах, precision проверенных алертов (>120 с),
средний lead time выданных алертов, число оценок, отдельные MAE модели и fallback,
latency последнего ML-запроса, средний throughput, очередь и статус потока.
KPI дашборда берутся из этих оценок. **Это development replay**: модель и её признаки
разрабатывались на этом дне, поэтому онлайн-публикация метрик не делает их независимой оценкой.
Исходы validate не открываются и не оцениваются.

## Деградация и демо

Кнопка статуса потока в верхней полосе выполняет настоящий обрыв TCP; повторное
нажатие разрешает reconnect. Виртуальное время продолжает идти. Сообщения в разрыве
теряются, а не добавляются задним числом. Эмулятор переподключается с backoff
0.5…15 реальных секунд. Backend сохраняет последнее положение с `is_stale`; ML
признаки продолжают соблюдать TTL и не получают просроченную позицию как свежую.

```bash
curl -X POST http://localhost:8000/api/demo/control \
  -H 'Content-Type: application/json' -d '{"action":"disconnect"}'
curl -X POST http://localhost:8000/api/demo/control \
  -H 'Content-Type: application/json' -d '{"action":"reconnect"}'
curl -X POST http://localhost:8000/api/demo/control \
  -H 'Content-Type: application/json' -d '{"action":"speed","speed":30}'
```

В разрыве прогнозы для ближайших событий используют медиану **уже опубликованных**
исходов плана; если её нет — последнее известное отклонение. Источник `historical`,
точный метод указан в `prediction_method`; это не результат ML.

Отказ ML:

```bash
docker compose stop ml
# backend остаётся доступен; новые запросы получают current_deviation_fallback
docker compose start ml
```

Health-проверка восстанавливает ML автоматически. Ошибки ML и длительность запроса
отражаются в метриках. Дашборд получает начальный WS snapshot, затем дельты раз в
секунду; после переподключения получает полный snapshot. Очередь на каждого клиента
ограничена, медленный браузер не задерживает приём NDTP.

## Проверки

```bash
.venv-services/bin/python -m pytest -q
docker compose config --quiet
.venv-services/bin/python scripts/smoke_dispatch.py
```

Smoke требует запущенный стек; проверяет REST, Swagger schema, WS snapshot/delta,
фактический обрыв, stale, reconnect, горизонты алертов и what-if. Он кратко меняет
состояние demo-потока и восстанавливает соединение в finally.

Браузерная проверка в отдельном headless Chrome (нужен установленный Chrome):

```bash
npm install --prefix /tmp/predictor-browser-test playwright-core
NODE_PATH=/tmp/predictor-browser-test/node_modules node tests/integration/dashboard_browser.cjs
```

`DASHBOARD_URL` задаёт адрес стенда (по умолчанию localhost:8080),
`CHROMIUM_PATH` — путь к альтернативному Chromium, `SCREENSHOT_PATH` — снимок экрана.
Проверка использует реальные REST/WS, проверяет слои карты, переключение планов,
масштабирование, сохранение камеры при обновлениях, клик по ТС и ответ what-if.


## Карта диспетчера

OpenLayers 10.10.0 хранится локально с BSD-лицензией в `dashboard/vendor`.
Подложка улиц — OpenStreetMap: обычная загрузка тайлов видимой области браузером,
с атрибуцией и HTTP-кэшированием, без массового скачивания. Для подложки нужен интернет;
операционные данные приходят только из backend. Телеметрия и планы не отправляются
в геокодеры/внешние маршрутизаторы. При ошибке тайлов показывается предупреждение,
локальные слои продолжают работать. Политика: https://operations.osmfoundation.org/policies/tiles/.

Камера сохраняется при обновлении WS; «Весь охват» возвращает все машины или полный
выбранный план. Подписи риска видны на общем масштабе, остальные подписи — при приближении.
Синий маркер означает отсутствие прогноза, серый — устаревшую позицию.
Сплошной трек — принятые GPS-точки последних 30 минут (`GET /api/map/tracks`, Swagger).
Точки собираются из уже выпущенных решений Cleaner; будущие и отвергнутые точки не
используются. Память ограничена 1800 точками на ТС. Отрисовка разрывает линии при
промежутках >120 с и скорости между точками >115 км/ч: это ограничение визуализации,
не изменение очистки/признаков. Полный план представлен пунктиром между контрольными
точками, без прежнего обрезания ±45 минут. Это не дорожный map matching.

Карточки сгруппированы по ТС (ближайшее будущее событие, иначе последнее ожидающее факт),
количество событий показано отдельно. KPI прогноза считает уникальные машины.
